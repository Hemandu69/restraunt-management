# Restaurant Management System

A real dine-in restaurant: a fixed set of dining tables, **Waiters** who take
orders/bills/payment at those tables, and a **Manager** who oversees the
business (staffing, menu, sales) rather than doing waiter work themselves.
There is no chef/kitchen role and no cashier role. See
`restaurant_management_system_requirements.md` for the full multi-phase spec
— note that a few of its older generic terms ("Staff") have been superseded
by the product decisions below.

So far this repo has **Authentication & Role Hierarchy only** — no tables,
orders, billing, payments, or menu module exists yet. Two things have been
built:

1. **App foundation** (`backend/`, `frontend/`): a working Express +
   Prisma/SQLite backend with its own JWT auth, and a React frontend.
2. **Supabase database foundation** (`supabase/`, `.github/workflows/`): a
   separate Postgres/Auth/RLS foundation on Supabase, with its own CI/CD,
   built in case the project moves onto Supabase.

   **These two are not currently connected.** `backend/`'s Prisma/SQLite/
   custom-JWT code is a fully separate, self-contained system from
   `supabase/`'s Postgres/Auth/RLS setup — the running app (`backend/` +
   `frontend/`) does not call Supabase at all today. Both were kept in sync
   on role terminology (`MANAGER`/`WAITER`) in this pass because both are
   real, working pieces of the repo, but *which one* (or what combination)
   ends up powering the real app is still an open decision for a future
   phase — see "Next phase" below.

## Product model

- **Manager** — overview and management. Primary question: *"How is my
  restaurant doing?"* Manages waiter accounts today; will manage the menu,
  see sales/revenue/order KPIs, and view reports once those modules exist.
  Never needs to do waiter work.
- **Waiter** — the operational user. Primary question: *"What tables need
  attention, and what orders/bills do I need to handle?"* Will select a
  table, take an order, add items, generate the bill, and take payment once
  those modules exist. Right now, logging in lands on a "Tables" placeholder.
- No Chef/Kitchen role or workflow. No Cashier role — billing is the
  Waiter's job. No account deactivation feature (see below) — that's not
  a current product concept, even though the underlying `status` field is
  kept in the data model for possible future account administration.

# Part 1: App foundation (Express + Prisma/SQLite)

## Architecture summary

| Layer | Choice | Why |
|---|---|---|
| Backend | Node.js + Express + TypeScript | Familiar, lightweight REST stack; easy to layer routes/controllers/services cleanly |
| Database | SQLite via Prisma ORM | Zero external services needed to run locally; swap `DATABASE_URL`/provider for PostgreSQL in production with no app code changes |
| Auth | JWT in an httpOnly cookie (`bcryptjs` password hashing) | Keeps the token out of reach of XSS/JS, while still returning the token in the login response body for non-browser clients (tests, curl) |
| Frontend | React + TypeScript (Vite) + React Router | Small, fast dev loop; router gives clean role-based route protection |
| Validation | Zod (backend) | Schema-based request validation with consistent error messages |
| Tests | Vitest + Supertest | Fast, TypeScript-native; used to cover auth and privilege-escalation scenarios |

Backend code is layered as `routes → controllers → services → Prisma`, with
`middleware/authenticate.ts` (identifies the user) and
`middleware/authorize.ts` (checks a permission) composed on top. Permissions
are declared in `backend/src/authorization/permissions.ts` as a role →
permission map, so future modules (tables, orders, billing, menu) add new
permissions there without touching authentication or the middleware itself.

# Part 2: Supabase database foundation

## Supabase setup

- **Supabase Auth** owns `auth.users` (credentials, sessions, sign-up/sign-in). Nothing in this repo re-implements authentication.
- **`public.profiles`** is the one application-owned table for this phase: `id` (FK to `auth.users.id`, `on delete cascade`), `name`, `role`, `status`, `created_at`, `updated_at`, `last_login_at`. It never stores a password.
- A trigger on `auth.users` (`handle_new_auth_user`) creates the matching `profiles` row on signup, **always** as `role = WAITER, status = ACTIVE` — client-supplied signup metadata (e.g. `{"role": "MANAGER"}`) is read only for a display-name fallback, never for role.
- Row Level Security is enabled on `profiles` with the minimum policies needed: a user can read and update their own row, but can never change `id`, `role`, or `status` on it, and can't read anyone else's row at all. See "RLS design" below.

## Supabase CLI installation

The CLI is not installed globally in this project — every command below is run via `npx` (works cross-platform, always uses a pinned-by-lockfile-free "latest", no global install to manage):

```bash
npx supabase --version
```

If you prefer a global install, see the [official install docs](https://supabase.com/docs/guides/local-development/cli/getting-started) (Scoop on Windows, Homebrew on macOS, or a direct binary download — **not** `npm install -g supabase`, which Supabase does not support).

You'll also need **Docker Desktop** running — `supabase start` runs Postgres, GoTrue (Auth), PostgREST, Studio, etc. as local containers.

## Local development

```bash
npx supabase init          # already done - creates supabase/config.toml (idempotent, safe to re-run)
npx supabase start         # boots the full local stack (Postgres, Auth, Studio, ...)
npx supabase db reset      # drops and recreates the local DB, replaying every
                            # migration in supabase/migrations/ + supabase/seed.sql
```

`db reset` is the reproducibility check: if it doesn't produce a working
database purely from what's committed in `supabase/migrations/`, the
migrations are wrong — never "fix" a broken local DB by hand-editing it in
Studio.

`supabase start` prints local URLs and keys (Studio at
`http://127.0.0.1:54323`, API at `http://127.0.0.1:54321`, plus an anon and
service-role key). These are well-known, publicly-documented **local dev
defaults** — safe to see in your terminal, but still not something to reuse
for a real project.

### Adding a schema change

```bash
npx supabase migration new <descriptive_name>   # creates a new timestamped, empty .sql file
# edit the generated file in supabase/migrations/
npx supabase db reset                           # verify it applies cleanly, locally
npx supabase test db                            # verify the pgTAP suite still passes
```

Commit the new migration file. Never edit a migration that has already been
applied to production (see "Production migration rules" below) — if the
schema needs to change further, that's another new migration. This is
exactly how the `MANAGER`/`STAFF` → `MANAGER`/`WAITER` rename was done: a new
`..._rename_staff_to_waiter.sql` migration (`alter type ... rename value` +
`create or replace function`), not an edit to the original migrations.

### Deploying to the linked Supabase project

```bash
npx supabase link --project-ref <your-project-ref>   # one-time per machine
npx supabase db push                                  # applies any migrations
                                                        # not yet in the remote
                                                        # history - never destructive
```

In this repo, `db push` to production is normally done by the
`database-deploy.yml` GitHub Actions workflow on merge to `main`, not by
hand — see "CI/CD" below.

## Database

**Enums**
- `public.user_role`: `MANAGER`, `WAITER`
- `public.user_status`: `ACTIVE`, `INACTIVE`

**Tables**
- `public.profiles` — see "Supabase setup" above for columns. Indexed on `role` and `status` (the two columns future waiter-management screens will filter/list by).

**Functions & triggers**
- `public.set_updated_at()` (generic, reusable) + `set_profiles_updated_at` trigger — keeps `updated_at` current on every update; uses `clock_timestamp()` rather than `now()` so it's accurate even within a single transaction (relevant for the test suite).
- `public.handle_new_auth_user()` (`SECURITY DEFINER`, explicit `search_path`) + `on_auth_user_created` trigger on `auth.users` — provisions the `profiles` row for every new signup, hard-coding `WAITER`/`ACTIVE`.

**RLS policies on `public.profiles`**
- `profiles_select_own` — `select`, `to authenticated`, `using (id = auth.uid())`
- `profiles_update_own` — `update`, `to authenticated`, `using (id = auth.uid())`, `with check` that the row's `id`, `role`, and `status` are unchanged from what's currently stored (so `name` can be updated, nothing security-relevant can)
- No `insert`/`delete` policies — rows are created only by the trigger above (which runs as the table owner, bypassing RLS) and removed only via the `on delete cascade` from `auth.users`.

**Migrations** (in order — each is one focused, reviewable change):

| File | Purpose |
|---|---|
| `..._create_user_enums.sql` | `user_role`, `user_status` enums |
| `..._create_profiles_table.sql` | `profiles` table + `role`/`status` indexes |
| `..._create_updated_at_trigger.sql` | reusable `set_updated_at()` + trigger |
| `..._create_profile_trigger.sql` | `handle_new_auth_user()` + trigger on `auth.users` |
| `..._configure_profile_rls.sql` | enables RLS + the two policies above |
| `..._enable_pgtap_extension.sql` | enables the `pgtap` extension used by the test suite |
| `..._rename_staff_to_waiter.sql` | renames the `STAFF` enum value to `WAITER`; updates the signup trigger's default |

## Authentication

`auth.users` (managed entirely by Supabase Auth — sign-up, sign-in, password
resets, sessions, JWTs) is the only place credentials live.
`public.profiles.id` is a foreign key to `auth.users.id` with
`on delete cascade`, so deleting an auth user always removes their profile
too, and every profile is guaranteed to correspond to a real auth user.
The application never queries or joins across this relationship manually
when creating a profile — the `on_auth_user_created` trigger does it
automatically and atomically as part of the signup transaction.

## Security: preventing WAITER → MANAGER self-promotion

Two independent layers, either of which alone would stop this:

1. **At signup**, `handle_new_auth_user()` never reads a `role` field from
   client-supplied metadata — it hard-codes `'WAITER'`. A signup request
   crafted with `{"data": {"role": "MANAGER"}}` still gets a `WAITER` profile
   (verified — see "Verification" below).
2. **After signup**, the `profiles_update_own` RLS policy's `with check`
   clause compares the row's `role` and `status` in the update against what
   is currently stored, and rejects the update (Postgres error `42501`,
   "new row violates row-level security policy") if either would change.
   This applies to *any* request made with a user's own session — including
   a Manager trying to change their own row — because RLS doesn't
   distinguish "nice" updates from malicious ones, it just enforces the
   invariant unconditionally for the `authenticated` role.

The only way to change a `role` or `status` is a request made with the
**secret/service-role key**, which has the `BYPASSRLS` attribute in
Supabase and therefore skips these policies entirely. That key is never
shipped to the frontend (see "Environment variables" below) — it is used
only by the local `promote-to-manager.mjs` script for now.

## Provisioning the first Manager

There is no public endpoint that lets anyone choose `role = MANAGER` — that
would defeat the whole point. Instead:

1. Create the user through Supabase Auth (sign up via the app once it calls
   `supabase.auth.signUp`, or via the Supabase Dashboard, or
   `supabase.auth.admin.createUser` from a trusted server context). They
   land as `WAITER`/`ACTIVE` automatically.
2. Find that user's UUID: Supabase Dashboard → Authentication → Users.
3. Run the provisioning script with the project's secret key:

   ```bash
   SUPABASE_URL="https://<your-project-ref>.supabase.co" \
   SUPABASE_SECRET_KEY="sb_secret_..." \
   node supabase/scripts/promote-to-manager.mjs <user-uuid>
   ```

## Type generation

```bash
cd backend  # or frontend
npm run db:types
```

This runs `supabase gen types typescript --local --workdir .. > src/types/database.types.ts`
in each package, regenerating `Database`/`Tables`/`Enums` types straight
from the local Postgres schema. Never hand-edit `database.types.ts` — after
any migration, re-run `db:types` in whichever package(s) consume it.

## Environment variables

`backend/.env.example` and `frontend/.env.example` each have a Supabase
section (placeholders only — see those files for the full picture including
Part 1's own variables):

- **Backend** (`SUPABASE_URL`, `SUPABASE_SECRET_KEY`): the secret/service-role key bypasses RLS. Server-side only — never send it to a browser, never log it, never commit a real value.
- **Frontend** (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`): the publishable/anon key is safe in the browser by design — it only ever grants what RLS policies allow.

## CI/CD

| Workflow | Trigger | What it does |
|---|---|---|
| `.github/workflows/database-test.yml` | `pull_request` → `main` (when `supabase/**` changed) | Boots an ephemeral local Supabase stack in the runner, runs `db reset` (full migration replay) and `supabase test db` (pgTAP). Fails the PR on any migration or test failure. Touches only the runner's local Docker containers — never the linked project, so it needs no secrets. |
| `.github/workflows/database-deploy.yml` | `push` → `main` (when `supabase/migrations/**` or `config.toml` changed) | Links the production project and runs `supabase migration list --linked` (sanity check) then `supabase db push --linked`. Never runs `db reset` against the linked project. |

### Required GitHub secrets

| Name | Used for |
|---|---|
| `SUPABASE_ACCESS_TOKEN` | Authenticates the CLI against the Supabase Management API |
| `SUPABASE_PROJECT_ID` | The production project's ref, used by `supabase link` |
| `SUPABASE_DB_PASSWORD` | The production project's Postgres password, needed by `supabase link`/`db push` to connect directly |

Set these under **Repo Settings → Secrets and variables → Actions**. None of
them are ever written into a workflow file or any other repo file.

### Production migration rules

**Never modify the production database schema manually through the
Supabase SQL Editor once migrations are established.** The only path from a
schema idea to production is:

```
developer → new migration → tested locally (db reset + test db)
   → committed → PR → database-test.yml passes → merge to main
   → database-deploy.yml runs `db push` → production
```

If a schema change is needed later, write another migration — never edit
one that has already shipped, since that rewrites history the production
database has already applied and desyncs it from what's in `supabase/migrations/`.
